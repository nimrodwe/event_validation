Event Validation

Synthetic events → localhost receiver → validate → pytest + Allure. Built so we can prove data quality without touching production.

In one minute

What we build

Generate catalog cases from a template, POST Base64 JSON to a local Flask receiver, GET them back, assert round-trip + rules.

Why a manifest

events.json = payload. manifest.json = intent (type, rule, headers). Same event can mean retry / replay / negative.

Two suites

Catalog — case types (POS/NEG/BND/…). Data types — each schema field fits (or deliberately doesn’t).

Extras

Local dashboard (pytest runs + shared CI panel), Allure on GitHub Actions → public allure-pages (no token), Docker for Mac/Windows parity.

template→ generator + manifest→ POST /v1/events→ GET store→ assert

How a test uses them

cases("negative") → keeps only manifest rows with type: "negative" → looks up the matching body in events by case_id → POST that body (plus delivery_headers if any) → assert. Same payload can appear twice (replay) with different headers.

test_type_ok Full walkthrough — think of parametrize as a for loop.

0) What @parametrize means (read this first)

# You write ONE function…
@pytest.mark.parametrize("field", TypeParams.POSITIVE_FIELD_NAMES)
def test_type_ok(initialize, catalog_receiver, field):
    … body …

# Pytest runs it like this:
# for field in ["app_build_number", "app_version", …, "threatcode", …, "timezone"]:  # 37 names
#     run test_type_ok(…, field)
#
# So you get 37 separate tests in the report:
#   test_type_ok[app_build_number]
#   test_type_ok[threatcode]
#   …
Parametrize in plain words
TypeParams.POSITIVE_FIELD_NAMES
A Python list of 37 strings — only names that exist in both the synthetic event and EventsSchema.
Example slice: ["app_build_number", "app_version", …, "threatcode", …, "timezone"]
@parametrize("field", that_list)
Tells pytest: call the function once per string.
Each call gets a different field argument.
The function body is identical every time — only field changes.
Why?
So we don’t write 37 copy-pasted tests. One loop of logic × many field names.

1) Where the 37 names come from (before any test runs)

Load good event
synthetic_event_template.json → {event, properties:{Threatcode:"XTAOPJ", UUID:"A000…0001", …}}
Load EventsSchema
List of columns: [{name:"threatcode", type:"String"}, {name:"uuid", type:"String"}, …]
SyntheticSteps.compare(event, schema)
for each key in properties:
  normalize "Threatcode" → "threatcode"
  if name is not in schema → skip (extra keys ignored)
  else keep {field:"threatcode", actual:"XTAOPJ", expected_type:"String"}
Result: list of 37 match dicts.
POSITIVE_FIELD_NAMES = [m["field"] for m in matches]
Just the names → fed into @parametrize.
