Event Validation

Synthetic events → localhost receiver → validate → pytest + Allure. Built so we can prove data quality without touching production.

In one minute

What we build

Generate catalog cases from a template, POST Base64 JSON to a local Flask receiver, GET them back, assert round-trip + rules.

Why a manifest

events.json = payload. manifest.json = intent (type, rule, headers). Same event can mean retry / replay / negative.

Two suites

Catalog — case types (POS/NEG/BND/…). Data types — each schema field fits (or deliberately doesn’t).

Extras

Local dashboard, Allure on CI (public per-run report), Docker for Mac/Windows parity.

template→ generator + manifest→ POST /v1/events→ GET store→ assert

How a test uses them

cases("negative") → keeps only manifest rows with type: "negative" → looks up the matching body in events by case_id → POST that body (plus delivery_headers if any) → assert. Same payload can appear twice (replay) with different headers.

What each catalog type does to data

TypeData changeWe assert
positive Unchanged template GET == sent + nested rules → no findings
negative Break one thing (empty UUID, null Threatcode, bad field, OS mismatch) GET == sent + expect values + nested rules → target finding
boundary Edge values (time=0, token len 29 / 30) Round-trip + edge rules
retry Same body, retry headers (count 1 then 2) Body + headers stored
duplicate Same payload twice (different case_ids) Round-trip + body fingerprint → DUP-NEAR (not UUID)
replay Same body twice, same case_id, replay headers GET count == posts (2→2) + bodies match

    for item in cases:

        rule_ids = [f["rule_id"] for f in findings]
